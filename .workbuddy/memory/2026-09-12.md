## What was done

User feedback after the first round of review said the previous design had
stacked too many CMA-ES-derived knobs (`c_σ, d_σ, c_c, c_1, c_μ, hsig, p_c`)
into the Flow Matching narrative.  The requested reformulation:

* one class, one step method, nine lines of body, ZERO user hyperparameters;
* every internal constant derived from `(D, N)`;
* algorithms stripped to their FM core: Sinkhorn OT pairing -> barycentric
  target -> constant velocity -> mean drift + rank-μ covariance update.

## Honest performance gap

At D=10, N=30, 200 iters, 5 seeds, vs. CMA-ES:
* wins: Sphere (machine zero), Rastrigin, Levy.
* ties: Ackley.
* loses: Rosenbrock (5.2 vs 0.15), Griewank (slight).

Root cause: pure rank-μ covariance update (no `p_c` rank-1 path).
The user explicitly chose simplicity.  If they later ask to close the
Rosenbrock gap, the natural single addition is `c_1 = alpha_C / D`
fed by the existing `p_sigma` path -- no new state, only one new constant.
Documented in MEMORY.md.

## GPU torch build (resolved)

The venv initially shipped `torch==2.14.0+cpu` (CPU-only wheel from the
default PyPI index -- `pip install -r requirements.txt` always grabs that).
That made `torch.cuda.is_available()` return False even on a CUDA machine.

Fix:
  pip uninstall -y torch
  pip install --index-url https://download.pytorch.org/whl/cu124 torch==2.6.0

Why 2.6.0 and not 2.14.0: the `cu124` PyTorch index only carries up to
2.6.0+cu124.  A later 2.x+cu124 wheel does not currently exist on that
mirror.  2.6.0+cu124 is fully compatible with RTX 3060 (sm_86).

After the swap:
  - `torch.cuda.is_available()` -> True
  - `FlowOpt(dim=10)` lands every state tensor on cuda:0 (`m, L, p_sigma, w`)
  - All 6 unit tests pass under cuda:0
  - `tutorial.ipynb` re-executes cleanly end-to-end on CUDA

## Notebook re-execution path (resolved)

`python -m jupyter nbconvert --execute` on Windows resolves to the Anaconda
`jupyter-nbconvert-script.py` because of the PATH order, which imports
torch from a Python interpreter that does NOT have torch installed.  This
yields a `ModuleNotFoundError: No module named 'torch'` even when the
kernel itself is correctly registered to `flowopt-env`.

Fix: invoke the flowopt-env binary directly:
  flowopt-env\Scripts\jupyter-nbconvert.exe --to notebook --execute --inplace tutorial.ipynb
This bypasses PATH-based resolution entirely; the binary's shebang pins it
to the venv Python.

## Tutorial notebook device portability (patched)

The CSA-null-hypothesis cell (Cell 15) called `torch.randn(N, D)` without
`device=`, so on a CUDA machine `opt.m` lived on cuda while the random
sample stayed on CPU and the addition raised a device mismatch.

Patched to `torch.randn(N, D, device=opt.device)` and the companion
`torch.randn(N)` to `torch.randn(N, device=opt.device).tolist()`.  The
patch runs on both CUDA and CPU -- it is device-agnostic.

The other cells either go through `opt.step()` (which uses `self.device`)
or use pure CPU tensors, so no other fixes were needed.

## Patch reversion (later same day)

When re-running the notebook end-to-end, Cell 15 again failed with the
device-mismatch error -- the `device=opt.device` patch from earlier had
been silently reverted.  Cause unclear (possibly an editor restore, an
auto-format, or a previous nbconvert run overwrote source).  Re-applied
the patch with a regex-based idempotent matcher.  Lesson: any device
fix in a notebook JSON should be applied via a script, not by hand, so
it can be re-applied reliably if it gets reverted.
